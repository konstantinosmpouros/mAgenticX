# Database Schema

This document describes the bridge's **`chat_db`** database (the render + relational store), accessed through an async SQLAlchemy engine backed by asyncpg. Its schema is defined in `src/dialogue_bridge/core/database/models.py` via SQLAlchemy ORM models and **versioned with Alembic** — migration files live in `src/dialogue_bridge/core/database/migrations/versions/` (`0001_baseline` → `0021_agent_tool_prefs`), applied via `alembic upgrade head` automatically on bridge startup (see the CLAUDE.md schema-change workflow). A separate **`agent_runtime`** database on the same Postgres instance is owned by the agents service and holds two things: LangGraph `AsyncPostgresSaver` checkpoints, and **`agent_memories`** (per-(user, agent) long-term memory — see [agent-memory](../flows/agent-memory.md)). Neither is part of these ORM models; that database has no alembic chain and its tables are created by `setup()` calls on boot. Memory lives there rather than here because the **agent** writes it mid-run, with no browser request to hang persistence off — and it means there is no FK to `users`, so deleting a user does not cascade to their memories. All primary keys are UUIDs generated by a server-side `gen_uuid()` helper. All timestamps are timezone-naive UTC. `updated_at` columns are maintained via SQLAlchemy's `onupdate=func.now()`.

## Table Reference

### `users`

The identity record for every person who has logged in. Created (or refreshed) on first successful Vault login via `upsert_user_from_vault()`.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `username` | `String` | No | — | UNIQUE, INDEXED — Vault username |
| `vault_user_id` | `String` | Yes | `NULL` | UNIQUE, INDEXED — Vault `entity_id`, stable across password changes. Nullable since `0014` (an Entra-only user has none). |
| `oidc_subject` | `String` | Yes | `NULL` | UNIQUE, INDEXED — Microsoft Entra `oid`. The OIDC counterpart of `vault_user_id`; a row may carry both when the account is linked across providers. |
| `auth_providers` | `String` | Yes | `NULL` | Comma-separated set of proven login methods (`vault`, `entra`) for observability; the subject columns are authoritative. |
| `email` | `String` | Yes | `NULL` | UNIQUE, INDEXED — the cross-provider **account-link key** (`upsert_user_from_identity`). May be `NULL` when no email is known. |
| `display_name` | `String` | Yes | `NULL` | From Vault metadata |
| `avatar_url` | `String` | Yes | `NULL` | From Vault metadata |
| `full_name` | `String` | Yes | `NULL` | From Vault metadata |
| `department` | `String` | Yes | `NULL` | From Vault metadata |
| `role_title` | `String` | Yes | `NULL` | From Vault metadata |
| `last_login_at` | `DateTime` | Yes | `NULL` | Updated on every successful login, before the session JWT is issued |
| `is_active` | `Boolean` | No | `true` | Set to `false` to ban a user at the application layer without touching Vault |
| `created_at` | `DateTime` | No | `func.now()` | — |
| `updated_at` | `DateTime` | No | `func.now()` | `onupdate=func.now()` |

**Relationships:** `preferences` (one-to-one, cascade delete), `conversations` (one-to-many, cascade delete).

### `agents`

Two different things share this table, and `owner_user_id` is the discriminator.
**Platform agents** (`owner_user_id IS NULL`) are upserted when the bridge fetches
the agents-service catalog — not created by user action. **User-authored agents**
carry an owner and their *definition* as well: since migration `0019`, `chat_db`
is the source of truth for it, and the agents-service volume is a cache
reconciled against these rows.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `owner_user_id` | `String` | Yes | `NULL` | FK → `users.id` CASCADE. `NULL` = a platform agent whose definition ships in the agents-service image |
| `slug` | `String` | No | — | Matches `BaseAgent.name` upstream. Unique per owner; platform slugs are globally unique via a **partial** index (see below) |
| `name` | `String` | No | — | Human-readable label |
| `description` | `String` | No | — | Shown in agent picker UI |
| `icon` | `String` | No | — | Icon identifier resolved by the UI |
| `version` | `String` | Yes | `NULL` | Semver string; nullable for legacy agents |
| `type` | `String` | No | `'langgraph agent'` | `"deep agent"` / `"langgraph agent"` / `"openai agent"` — lets the UI show only features a kind supports (e.g. per-agent skills) |
| `is_active` | `Boolean` | No | `true` | Inactive agents are hidden from the picker. **Also the delete tombstone** for authored agents: delete is soft because `conversations.agent_id` cascades, and reconciliation reads a dormant row as "remove the folder", never "materialise it" |
| `definition_spec` | `JSON` | Yes | `NULL` | The authored `AgentSpec`, for user agents only. Stores the **submitted payload**, not the generated `agent.yaml` — that file is derived from this spec upstream and uploading one is rejected, so the spec is the real input, and keeping it spares the bridge a YAML dependency |
| `created_at` | `DateTime` | No | `func.now()` | — |
| `updated_at` | `DateTime` | No | `func.now()` | `onupdate=func.now()` |

**Relationships:** `conversations` (one-to-many, cascade delete), `definition_files` (one-to-many, cascade delete).

**Two uniqueness rules, not one.** `uq_agents_owner_slug` on `(owner_user_id, slug)` stops a user having two agents with the same slug. That alone is not enough for platform agents: Postgres allows unlimited `NULL`s under a unique index, so a partial index `uq_agents_global_slug` on `slug WHERE owner_user_id IS NULL` keeps platform slugs globally unique.

### `agent_definition_files`

The prompt files of a user-authored agent — `AGENT.md`, sub-agent prompts, and anything else the builder submitted. Added in `0019`.

Before this, a definition existed **only** on the agents-service volume, which has no backup: losing it left the catalog row pointing at nothing — an agent that listed in the UI and failed the moment you ran it.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `agent_id` | `String` | No | — | FK → `agents.id` CASCADE, indexed |
| `path` | `String` | No | — | Relative path inside the agent folder, e.g. `AGENT.md`, `subagents/writer.md` |
| `content` | `Text` | No | — | UTF-8. Text rather than `bytea` because the upload allowlist is `.md/.txt/.yaml/.yml`, so base64 would be dead weight |
| `updated_at` | `DateTime` | No | `func.now()` | `onupdate=func.now()` |

`UNIQUE (agent_id, path)`. A save **replaces** the whole file set rather than merging into it — the builder contract deletes any file the user did not re-send, so merging here would leave `chat_db` holding files the volume no longer has.

| `created_at` | `DateTime` | No | `func.now()` | — |

### `messages`

Every chat turn — both user and AI — is a row in this table. The `parent_message_id` self-reference enables branching: when a user edits a message or retries an AI response, a new sibling row is created under the same parent rather than overwriting the existing row.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `conversation_id` | `String` | No | — | FK → `conversations.id` CASCADE, INDEXED |
| `parent_message_id` | `String` | Yes | `NULL` | FK → `messages.id` SET NULL, INDEXED — self-reference for branching |
| `sender` | `MessageSenderEnum` | No | — | `"user"` or `"ai"` (Postgres enum `message_sender_enum`) |
| `content` | `Text` | Yes | `NULL` | Message body; `NULL` for placeholder rows created before inference completes |
| `liked` | `Boolean` | Yes | `NULL` | Three-state: `NULL` = not rated, `true` = liked, `false` = disliked |
| `agent_id` | `String` | Yes | `NULL` | FK → `agents.id` SET NULL, INDEXED — the agent that produced this message. Set on AI run messages; `NULL` on user messages. Per-message attribution lets one conversation mix agents. |
| `agent_name` | `String` | Yes | `NULL` | Denormalized agent label captured at run time, so a deactivated/removed agent still renders in the message action bar (mirrors `conversations.agent_name`). |
| `reasoning_steps` | `JSON` | Yes | `NULL` | Array of thought strings accumulated during inference |
| `reasoning_time_seconds` | `Integer` | Yes | `NULL` | Thinking duration in whole seconds |
| `input_tokens` | `Integer` | Yes | `NULL` | Per-message input tokens, summed across all model calls + sub-agents in the turn (true billed consumption — each call re-sends context). AI-run messages only; `NULL` on user/historical rows. Added in migration `0004`. |
| `output_tokens` | `Integer` | Yes | `NULL` | Per-message output tokens, summed across the turn. AI-run messages only; `NULL` otherwise. Migration `0004`. |
| `checkpoint_thread_id` | `String` | Yes | `NULL` | INDEXED (`ix_messages_checkpoint_thread_id`) — the per-branch LangGraph thread this run resumed from / created in the agents-service durable checkpointer. Shared across all runs on a branch; minted fresh on edit/retry (copy-on-fork). Looked up to resolve a branch's thread and to reap a conversation's threads on delete. Set on AI-run messages; `NULL` on user/pre-migration rows. Added in migration `0007`. |
| `checkpoint_id` | `String` | Yes | `NULL` | The durable checkpoint head this run committed, captured from the terminal `CHECKPOINT_COMMITTED` AG-UI event. Used by edit/retry to fork from the right point. AI-run messages only; `NULL` otherwise. Migration `0007`. |
| `is_error` | `Boolean` | No | `false` | `true` when the inference run that produced this message failed |
| `error_message` | `Text` | Yes | `NULL` | Error detail when `is_error=true` |
| `raw_events` | `JSON` | Yes | `NULL` | The **full per-run AG-UI event log** (every event, seq-stamped, with consecutive text/tool-args deltas coalesced and oversized `TOOL_CALL_RESULT` content truncated + flagged). The UI replays this into the rendered run timeline — including the agent plan (from `PLAN_SNAPSHOT` events) and sub-agent activity (from `SUBAGENT_EVENT`), which are no longer persisted as their own columns. Rows persisted before the timeline rebuild contain only `CUSTOM` events — the UI's legacy fold covers them. |
| `streaming_status` | `String` | Yes | `NULL` | INDEXED (partial, `IS NOT NULL`) — `"queued"`, `"running"`, `"cancelling"`, `"completed"`, `"cancelled"`, `"failed"`. `NULL` on user messages and on AI messages that were not produced by a detached run. |
| `streaming_message_path` | `JSON` | Yes | `NULL` | Ordered list of message IDs representing the branch path the agent saw as history when the run was started |
| `streaming_started_at` | `DateTime` | Yes | `NULL` | Run creation timestamp; sorts the run list endpoint |
| `streaming_completed_at` | `DateTime` | Yes | `NULL` | Set on terminal status transition |
| `streaming_cancel_requested_at` | `DateTime` | Yes | `NULL` | Set when the client requests cancellation |
| `scheduled_task_id` | `String` | Yes | `NULL` | FK → `scheduled_tasks.id` SET NULL, INDEXED — set on AI run messages produced by a scheduled-task fire; the durable "this run came from task X" tag. SET NULL so deleting a task never deletes the runs it produced. Migration `0009`. |
| `created_at` | `DateTime` | No | `func.now()` | — |
| `updated_at` | `DateTime` | No | `func.now()` | `onupdate=func.now()` |

**Relationships:** `conversation` (many-to-one), `attachments` (one-to-many, ordered by `created_at ASC`, cascade delete).

**The assistant message is the inference run.** There is no separate `inference_runs` table — the `streaming_*` columns on the AI `MessageTable` row carry the full run lifecycle. `InferenceRunRuntime` keeps the seq-stamped coalesced event log plus the flat aggregates (`content`, `reasoning_steps`, `plan`, `subagents`) in memory during the stream; on terminal write, those values plus the final `streaming_status` are persisted to the same row in a single transaction. The `InferenceRunOut` API shape is built from the row by `build_run_out_from_message(...)`, and `MessageOut` exposes `streaming_status` as `streamingStatus` so the client's Done sentinel can distinguish completed/cancelled/failed on hydration. Note the storage implication of the full log: `raw_events` now grows with run length (text and sub-agent activity are stored once in the log, with delta coalescing and tool-result truncation keeping it bounded); no DDL changed — the column was already `JSON`.

**Partial indexes on `messages`:**

```sql
CREATE UNIQUE INDEX uq_messages_one_active_stream_per_conversation
  ON messages (conversation_id)
  WHERE streaming_status IN ('queued', 'running', 'cancelling');

CREATE INDEX ix_messages_streaming_status
  ON messages (streaming_status)
  WHERE streaming_status IS NOT NULL;
```

The unique index enforces at most one active stream per conversation at the database level — a concurrent attempt to start a second run while one is still active raises a unique-constraint violation. The non-unique index supports the run-list endpoint's filter on `streaming_status IN (...)` without scanning the full table (only ~the active and recently-terminal AI rows are indexed).

A third, plain (non-partial) index `ix_messages_checkpoint_thread_id` on `checkpoint_thread_id` (migration `0007`) supports resolving a branch's durable LangGraph thread and reaping a conversation's checkpoint threads on delete.

### `attachments`

Metadata for every file attached to a message. The binary data lives in the `blobs` table; `attachments` is the linkage record. One message can have up to 10 attachments (validated by Pydantic, not a DB constraint). Total size per message is capped at 25 MB. An attachment is either a **user upload** (`origin = 'upload'`) or an **agent-generated deliverable** (`origin = 'generated'`) — the latter is written onto the *assistant* message at run finalize when a deep agent designates an output file via the `present_artifact` tool (see [conversation-management / attachments flow](../flows/attachments.md)).

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `message_id` | `String` | No | — | FK → `messages.id` CASCADE, INDEXED |
| `blob_id` | `String` | Yes | `NULL` | FK → `blobs.id` CASCADE, INDEXED — `NULL` only during a brief window between attachment record creation and blob upload |
| `file_name` | `String` | No | — | Original filename (upload) or the presented file's basename (generated) |
| `mime_type` | `String` | No | — | MIME type declared by the uploader, or guessed from the generated file's extension |
| `size_bytes` | `Integer` | Yes | `NULL` | File size in bytes |
| `origin` | `String` | No | `'upload'` | `'upload'` (user-attached) \| `'generated'` (present_artifact deliverable). Added in migration `0013`; backfilled to `'upload'` for all pre-existing rows |
| `title` | `String` | Yes | `NULL` | Agent-supplied display title — generated artifacts only |
| `summary` | `String` | Yes | `NULL` | Agent-supplied one-line description — generated artifacts only |
| `created_at` | `DateTime` | No | `func.now()` | — |
| `updated_at` | `DateTime` | No | `func.now()` | `onupdate=func.now()` |

**Relationships:** `message` (many-to-one), `blob` (one-to-one, cascade delete, `single_parent=True`).

### `user_agent_tool_prefs`

One tool the user turned OFF or ON for a specific agent (the Agents tab). Added in `0021`.

An agent declares a baseline tool set and the always-on native builtins sit on top; the effective set at build time is `(declared ∪ user_enabled) − user_disabled`. These overrides used to live only in `<agent_root>/tool_prefs.json` on the agents-service volume, which has no backup — losing it silently reverted every user's tool choices to the declared baseline.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | `String` | No | `gen_uuid()` | PK |
| `user_id` | `String` | No | — | FK → `users.id` CASCADE, indexed |
| `agent_slug` | `String` | No | — | The agent **slug**, indexed — the pairing is meaningful for platform agents too |
| `tool_key` | `String` | No | — | Canonical tool-cache-key: `<server>/<tool>` for MCP, the bare name for native. Stored **verbatim** — the runtime matches it against live tools by this exact string, so normalising it differently would silently stop matching |

### `message_embeddings`

One semantic embedding per message (**pgvector**), powering "most relevant conversations for a query" retrieval — the foundation for cross-chat search and memory. Kept in its own table (not a column on `messages`) so the hot message table stays lean and embeddings can be regenerated/versioned independently. ## Notable Design Decisions

### Message Branching via Self-Reference

`messages.parent_message_id` is a self-referential FK. Every message in a conversation has exactly one parent (or `NULL` for the root). When a user edits a message or retries an AI response, a new sibling row is created under the same parent — the existing row is never overwritten. The UI selects a path through this tree by traversing `parent_message_id` chains; the `streaming_message_path` column on the AI `messages` row stores the selected branch as an ordered list of IDs captured at inference start.

There is no `position` or `order` column — the canonical ordering within a branch is `created_at ASC`.

### Denormalized `agent_name` on Conversations

`conversations.agent_name` mirrors `conversations.agent_id` as a denormalized last-used label. Per-message attribution is the source of truth: each AI message carries its own `agent_id` + `agent_name`, so a conversation can mix agents and every message renders the agent that produced it. The conversation-level pair is updated to the latest run's agent (used for the sidebar/header default and the picker seed on conversation switch).

### `active_assistant_message_id` and `post_update`

`conversations.active_assistant_message_id` creates a circular reference with `messages` (the `messages.conversation_id` FK points back at `conversations`). SQLAlchemy's `post_update=True` on the `active_assistant_message` relationship breaks the insert-ordering deadlock by issuing the `conversations` UPDATE in a second round-trip after the initial AI placeholder `INSERT INTO messages`.

### `blobs` Has No `updated_at`

Blobs are write-once. Once a file is uploaded, its binary content never changes. `blobs` therefore has only `id`, `data`, and `created_at`. The associated `attachments` metadata row may be updated (e.g., `blob_id` set after initial creation), but the blob itself is immutable.

### JSON Columns for AG-UI State

`messages.raw_events`, `messages.plan`, and `messages.subagents` store structured AG-UI event data as Postgres JSON. This avoids normalizing a rapidly-evolving event schema into relational tables. During streaming these columns are `NULL` — the live in-flight state lives in the per-task `InferenceRunRuntime` accumulator (process memory) and is mirrored into the durable Redis stream at `inference:run:{message_id}:events`. On terminal write, the accumulator's final state is persisted to the row's JSON columns in a single atomic commit alongside `streaming_status` and `streaming_completed_at`.

### `conversation_shares.snapshot_json` is a Frozen Copy

The share snapshot is stored entirely in `snapshot_json` — a point-in-time JSON copy of the conversation and its messages. Shared links remain stable and readable even if the original conversation is deleted. Accessing a share does not query `conversations` or `messages` at all.

## Sharp Edges and Behavioral Notes

- **Schema changes go through Alembic migrations.** Edit the ORM model in `core/database/models.py`, then autogenerate + hand-review a migration in `core/database/migrations/versions/` (the ordered chain `0001_baseline` → `0016_retire_enabled_tools`). `alembic upgrade head` runs automatically on bridge startup. Never use `metadata.create_all`. See the CLAUDE.md "Schema Changes — Migration Workflow" section.

- **Tool enablement left this database in `0016`.** Migration `0016_retire_enabled_tools` (down_revision `0015_personalization`) dropped `user_preferences.tools`, `messages.streaming_enabled_tools`, and `scheduled_tasks.enabled_tools` in one step. The global "enabled tools" model is gone entirely — tools are declared per agent (`agent.yaml`) and disabled per (user, agent) on the agents service (`tool_prefs.json`). Nothing in `chat_db` records tool enablement anymore.

- **All IDs are UUIDs stored as `String`, not the native Postgres `UUID` type.** This avoids a SQLAlchemy/asyncpg type handling quirk but means the database does not reject malformed IDs at the storage layer — only application code validates UUID format.

- **`messages.content` is `NULL` for placeholder rows.** When inference starts, the AI message row is created immediately with `content=NULL`. It is populated only when `_finish_run()` commits the terminal state. Any query that joins messages and assumes `content IS NOT NULL` will silently miss in-flight rows.

- **`conversation_shares.snapshot_json` is stored inline, not in `blobs`.** Large conversations with many messages produce large JSON values stored directly in the Postgres row. There is no size cap enforced by the schema.

- **The partial index conditions are string literals.** If the set of active status strings ever changes (e.g., a new `"pausing"` status is added), the `uq_messages_one_active_stream_per_conversation` and `ix_messages_streaming_status` WHERE clauses must be updated manually — they do not reference the application's `ACTIVE_RUN_STATUSES` constant.

- **`conversations.active_assistant_message_id` is SET NULL on message delete, not on streaming-status change.** The column is updated programmatically when the AI message transitions to a terminal `streaming_status`. A crash between terminal write and the `UPDATE conversations SET active_assistant_message_id = NULL` leaves the column pointing at a completed message until the next startup cleanup pass.

- **The durable in-flight event log is in Redis, not Postgres.** Chunks streamed during a run are appended to the Redis Stream `inference:run:{message_id}:events` via `RedisEventLog.append(...)`. Postgres only sees the terminal snapshot when `_finish_run()` commits. Killing the bridge mid-stream leaves the AI row in `streaming_status='running'`; the startup cleanup pass (`cleanup_orphaned_inference_runs`) transitions any abandoned rows to `failed`.

- **`users.email` allows `NULL` with a UNIQUE constraint.** Postgres treats each `NULL` as distinct, so multiple users with no email on record do not violate the constraint. The UNIQUE index only prevents two rows from sharing the same non-null email value.
